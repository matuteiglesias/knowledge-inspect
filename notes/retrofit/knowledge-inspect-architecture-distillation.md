## 2. Architecture in one paragraph

Knowledge Inspect has a small active product spine and a separate, partially stranded experimental layer. Four module CLIs call three product orchestrators plus one payload validator. The orchestrators own chat parsing/embedding/persistence, chat summarization/export, and an external GROBID wrapper. A shared run-evidence kernel constructs and finalizes run records, run-bundle manifests, and per-operator latest pointers. `KBConfig` locates operational state and public evidence. Ingest uses a parser, a durable embedding cache, processed-file ledger, and Chroma helpers; analyze prefers the newest chunk set by filesystem modification time and otherwise reads Chroma. Alongside this spine are unreferenced embedding and Chroma compatibility experiments, a duplicate Chroma client file, tracked bytecode, and stale operational notes. Those are candidates for bounded retirement, but only generated bytecode is proven semantically unnecessary from repository evidence alone.

## 6. Invariants worth preserving

1. One stable operator CLI per product seam, with current exit-code meanings; validator remains a separate diagnostic CLI.
2. Every product run attempts to emit final run evidence even on payload/provider failure.
3. Final statuses remain constrained and structured errors/warnings/counters/stages remain inspectable.
4. Chunk IDs remain derived from source/header/text; Chroma writes remain idempotent.
5. Cached embedding work is committed frequently and processed inputs are marked only after successful processing; smoke/dry-run side-effect boundaries remain intact.
6. Chunk-set, summary, Markdown, run-record, bundle, and latest filenames/shapes remain compatibility surfaces until versioned deprecation.
7. Latest remains module-local and per operator; it is not silently promoted to global discovery.
8. GROBID remains an optional adapter boundary rather than forcing paper internals into the chat core.
9. Provider and storage implementations may change behind seam behavior; operational ordering/recovery semantics may not change accidentally.
10. Historical artifacts are never rewritten as cleanup.

## 10. Practical target architecture

The desired lean system is not a new framework. It is the current active spine with boundaries made explicit:

1. **Operator layer:** four small CLIs.
2. **Product layer:** three independent orchestrators with explicit inputs/results.
3. **Governance kernel:** one run-evidence implementation and approved public projections.
4. **Payload layer:** parser/chunk contract and summary/export semantics owned by their seams.
5. **Ports at expensive/external boundaries:** one explicit embedding provider interface, one active Chroma gateway, one GROBID adapter.
6. **Operational state:** cache, ledger, and vector store remain private but their ordering/recovery invariants are tested.
7. **Evidence layer:** immutable run artifacts plus mutable module-local discovery.

This target deletes no capability. It removes conceptual burden by retiring alternate implementations, generated residue, missing-package experiments, and hidden discovery only after evidence and deprecation. Every addition has a deletion/simplification purpose: the provider port removes provider construction from orchestration; explicit discovery removes mtime selection; focused recovery tests permit safe storage changes; no other abstraction is currently justified.

### Ordering and stale-reference hazards

1. The finalizer computes the final status/time, registers run/manifest/latest artifact records, writes latest, marks the contract stage complete, writes the run record, computes member hashes, writes the bundle, and has already changed the run record before/around hashing. Latest can transiently or permanently point to missing/incomplete evidence if later operations fail.
2. The manifest’s run-record hash can describe bytes before the subsequent run-record rewrite; checksum verification must not be strengthened by assertion alone—write ordering or checksum scope needs a versioned fix.
3. Ingest caches embeddings before Chroma/file completion and marks the file processed only after batching succeeds. That partial cache is deliberate recovery value. Cache, ledger, and Chroma are not one transaction and must not be “simplified” into all-or-nothing deletion.
4. A caller-selected Markdown name can be overwritten by a later analyze run while old summaries retain prior text/path, so path identity does not uniquely identify immutable artifact bytes.
5. Analyzer mtime discovery is a second latest mechanism unrelated to the operator latest pointer; concurrent/copy operations can make it select a semantically unexpected chunk set.

## 21. Phase J — minimal target architecture

### Target shape

```text
CLI adapters
  kb_chat_ingest | kb_chat_analyze | kb_papers_grobid | kb_validate_chunk_set
        ↓
seam orchestrators
  ingest_paths   | analyze         | run_pdf          | validate payload
        ↓
shared operational kernel
  configuration snapshot · run lifecycle · structured failure · atomic write
        ↓
payload-specific writers
  chunk_set.v1   | summary.v1 + Markdown | TEI reference | diagnostics
        ↓
artifact and run evidence
  payloads · run record · run-bundle manifest · checksums
        ↓
module-local discovery surfaces
  operator latest · future explicit payload selection/index

External/local adapters, called inward only by the owning seam:
  chat source reader/parser · embedding provider · Chroma · GROBID · filesystem resolver

Private operational state:
  embedding cache · processed-file ledger · Chroma collection
```

### Permitted dependency direction

1. CLI adapters may depend on their one seam API and presentation/argument parsing only.
2. Seam orchestrators may depend on the shared operational kernel, their payload writer/contract, and small explicit external adapters.
3. The operational kernel may depend on standard-library filesystem/time/hash/serialization primitives and a narrow artifact-root/config value; it must not import seam payloads, providers, Chroma, GROBID, or CLI code.
4. Payload writers may depend on their schema/domain representation and atomic serialization primitive; they must not publish latest or choose provider/storage behavior.
5. Adapters may depend on external libraries/services. External adapters must not assign public producer, run, or artifact identity.
6. Discovery may read completed evidence/payload references but must not import orchestration internals or infer identity through normalization.
7. State/recovery modules remain below the owning seam; no public consumer should import their database or Chroma implementation.

Reverse dependencies—kernel to seam, payload to provider, adapter to CLI, or external package to local identity policy—are prohibited. Cross-repository runtime imports remain prohibited; GROBID is an external runtime adapter, not permission to import paper-kb.

### Ownership table

| Concept | Canonical owner | Rules |
|---|---|---|
| repository/module/producer identity mapping | reviewed module descriptor/governance constants, projected by operational kernel | explicit table; legacy `kb` values retained; no fuzzy normalization |
| entrypoint identity | each CLI/seam declaration | underscore CLI spelling remains public |
| operator identity | operational kernel/seam declaration | dotted identity owns latest filename; distinct from entrypoint |
| run ID and timestamps | operational kernel | stable generation/collision policy; UTC lifecycle; adapters cannot override |
| final run status | operational kernel from seam-requested outcome, errors and approved counters | preserves four current values/mapping until versioned migration |
| stage status/details | seam declares stages; operational kernel applies transitions | stage and run status remain separate dimensions |
| artifact logical identity/family/kind | payload-specific writer under approved shared mapping | never inferred solely from filesystem path or provider |
| payload serialization and ordering | payload-specific writer (`chunk_set`, summary/export, TEI adapter reference) | schema/version owned beside payload; deterministic order pinned where contractual |
| run-record and bundle serialization | operational kernel | convenience aliases remain compatibility projections |
| checksums | evidence finalization within operational kernel, after immutable payload bytes are final | no unverifiable self-cycle; pointer is published only after members validate |
| latest publication | operational kernel/discovery publisher | module-local, per operator, pointer last; payload selection is separate and explicit |
| embedding/cache/Chroma recovery ordering | ingest seam plus bounded adapters/state modules | implementation can change; cache/idempotence/mark-after-success invariants cannot |
| source selection | CLI/API explicit input plus filesystem resolver | explicit selection first; legacy mtime fallback only during migration |

### Interfaces justified by current implementations

- **Embedding callable:** justified because `_make_embed_fn` already returns the same callable shape for two provider implementations and `SQLiteVecCache.cached_embedder` consumes it. Keep this as a function/protocol of one operation, not plugin discovery.
- **Chroma gateway modules:** justified because two seams share client/collection creation and I/O functions. Retain concrete Chroma naming; there is only one real storage implementation, so a generic vector repository interface is not justified.
- **GROBID callable boundary:** justified by the existing single delegated `run` call and optional runtime. A thin typed wrapper/fixture is enough; no paper-processing framework.
- **Filesystem chunk resolver:** justified by current mtime selection and the need for explicit selection/fallback. It returns a selected `Path` plus provenance; it is not a generic artifact repository.
- **Compatibility reader/projection:** justified only when shared/historical versions coexist. It must preserve raw fields and dispatch on explicit versions, not heuristic normalization.
- **Recovery verifier:** justified by current multi-file transaction windows. Begin read-only; mutation/latest repair is a separate explicitly invoked operation.

### Explicitly rejected additions

The target contains no universal pipeline framework, dependency-injection container, plugin discovery, event bus, generic repository abstraction, new database, workflow engine, MCP integration, or cross-repository runtime import. Current evidence shows three distinct seams, one concrete Chroma store, one SQLite recovery file, one optional GROBID adapter, and two explicit embedding providers; none justifies those mechanisms.

### Sequence rule

The ordering is intentional: remove only proven generated noise, make health checks deterministic, pin current recovery and public behavior, isolate expensive dependencies, repair evidence correctness additively, observe consumers, and only then delete deprecated alternatives or aliases. A stage must not bundle hygiene, behavioral refactoring, schema migration, and source deletion into one review.
